

**CIV verification chain**

Requirements and threat model

Mathematical and system specifications

Kernel implementation proofs

Compiler, linker, and binary verification

Boot, hardware contracts, and deployed-system validation

A proof at one layer does not automatically prove the layer below it. That distinction is where a lot of supposedly verified systems quietly become less verified.

## **1. Recommended core toolchain**

These are the tools I would actually put into CIV's engineering plan.

| Tool                                 | Primary responsibility                                      | Why CIV needs it                                                                                         |
| ------------------------------------ | ----------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Isabelle/HOL                         | Kernel and system-level proofs                              | Mature higher-order logic, strong proof infrastructure, and precedent from the seL4 verification project |
| Verus                                | Verification of Rust implementation                         | Proves functional correctness and safety properties of Rust code using specifications and SMT            |
| Lean 4                               | Mathematical foundations and independent specifications     | Useful for precise definitions, mathematical models, and machine-checked theorems                        |
| TLA+                                 | Concurrency and distributed protocols                       | Models schedulers, locks, interrupts, device protocols, and state transitions                            |
| TLC                                  | State-space exploration                                     | Finds deadlocks, races in modeled protocols, and invalid state transitions                               |
| Z3                                   | Constraint solving and proof automation                     | Discharges verification conditions generated by Verus and other tools                                    |
| cvc5                                 | Independent SMT solving                                     | Provides a second solver for supported theories and catches solver-specific issues                       |
| Kani                                 | Bounded verification of Rust                                | Checks assertions, panic paths, memory-related behavior, and bounded execution paths                     |
| CBMC                                 | Verification of low-level C/C++ and selected generated code | Useful for firmware-facing code, C interfaces, and small low-level components                            |
| Q3B or another maintained QBF solver | Quantified Boolean reasoning                                | Checks finite adversarial games and quantified Boolean models                                            |

I would also include:

- Rocq for proof developments that benefit from its mature ecosystem and existing verified-software libraries.
- F\* for cryptographic code and components where refinement types and effect reasoning are useful.
- Alloy for exploring architectural relationships, capability graphs, and access-control models.
- Ghidra for binary inspection and audit support. It is not a theorem prover.
- QEMU for execution testing across virtual hardware configurations. It is not proof of hardware correctness.

## **2. What each tool should prove**

### **Isabelle/HOL: the system-level mathematical authority**

Use Isabelle/HOL for the most important abstract system properties:

- Kernel state invariants.
- Process and thread lifecycle correctness.
- Address-space isolation.
- Capability derivation and revocation.
- Memory-management invariants.
- Interrupt and exception state transitions.
- Scheduler correctness.
- System-call semantics.
- Refinement between abstract kernel operations and concrete implementations.

The key idea is to define an abstract CIV machine and prove that every permitted operation preserves its invariants.

For example:

\\[ \forall s.\ \operatorname{Invariant}(s) \land \operatorname{ValidOperation}(op,s) \Rightarrow \operatorname{Invariant}(\operatorname{step}(s,op)) \\]

That is a basic invariant-preservation obligation, not the whole verification story.

### **Verus: implementation-level Rust verification**

Use Verus for the actual Rust kernel implementation.

Its job is to verify properties such as:

- Pointer and memory-access safety.
- Data-structure invariants.
- Correctness of page-table manipulation algorithms.
- Ownership and resource-accounting properties.
- Correctness of capability-table operations.
- Locking and synchronization properties within its supported reasoning model.
- Functional correctness of critical routines.

Important: Verus proofs do not automatically prove that the Rust compiler preserves those properties in the final executable. That needs its own assurance boundary.

### **Lean 4: mathematical specifications**

Use Lean 4 for independent, precise mathematical models.

Good targets include:

- Integer and bit-vector arithmetic.
- Page-table indexing and address translation.
- Cryptographic constructions and protocol mathematics.
- Memory allocator properties.
- Scheduling and fairness definitions.
- Proofs about data structures and algorithms.

I would avoid maintaining duplicate versions of every theorem in Lean and Isabelle. That creates two proof systems that can disagree while everyone congratulates themselves.

Use Lean where its mathematical ecosystem helps, and Isabelle as the primary system-level proof environment.

### **TLA+ and TLC: concurrency**

Use TLA+ to model systems whose correctness depends on the ordering of events.

Examples:

- Thread creation and destruction.
- Scheduler transitions.
- Interrupt arrival during context switching.
- Lock acquisition and release.
- Device reset and recovery.
- DMA buffer ownership.
- Driver shutdown while requests remain outstanding.
- CPU hot-plug and power-state transitions, if supported.

Model both expected behavior and adversarial interleavings.

TLC can exhaustively explore finite models. It cannot exhaustively explore an unbounded real operating system, so the model's scope and bounds must be recorded.

### **Z3, cvc5, and QBF solvers: automated reasoning**

Use SMT solvers for arithmetic, bit-vectors, arrays, and logical verification conditions.

Use QBF solvers for explicitly finite quantified problems, such as:

\\[ \exists D\ \forall A.\ \operatorname{Safe}(D,A) \\]

Here, \\(D\\) might represent a defensive policy and \\(A\\) an attacker strategy. The actual quantifier order must reflect who chooses what, when, and with what information.

For more complex exploit models, use multiple stages of attacker and defender choices. Do not pretend that a single QBF query can represent every exploit.

**Critical limitation:** An unsatisfiable result only excludes the attack represented by that particular model, assumptions, and bounds. It does not establish that the real system has no exploit.

## **4. The difficult part: compiler and binary verification**

This is where CIV's end-to-end requirement becomes genuinely expensive.

Suppose the kernel is written in Rust. A proof that a Rust function is correct does not, by itself, prove that:

1. The Rust compiler translated it correctly.
2. LLVM preserved its semantics.
3. The assembler encoded the intended instructions.
4. The linker produced the intended layout.
5. The bootloader loaded the correct binary.
6. The processor executed the instructions according to the assumed architecture.

CIV needs a defined chain of assurance.

I would specify these components:

| Component                  | Verification requirement                                                 |
| -------------------------- | ------------------------------------------------------------------------ |
| Rust source                | Functional correctness and memory safety                                 |
| Compiler                   | Correctness of transformations, or a justified trusted compiler boundary |
| LLVM optimization pipeline | Validated transformations and compiler testing                           |
| Assembly                   | Instruction-level specification and reviewed implementation              |
| Linker                     | Layout, relocation, symbol, and section invariants                       |
| Executable                 | Static binary checks and selected machine-code proofs                    |
| Bootloader                 | Verified loading, authentication, and handoff                            |
| CPU                        | Explicit ISA and hardware assumptions                                    |
| Runtime                    | Evidence that deployed configuration matches verified configuration      |

A realistic initial strategy is to keep the trusted computing base explicit, minimize it, and verify more of it over time. A fully verified Rust-to-x86-64 toolchain would be a major independent research project.

```
│   ├── adversarial-models/
│   ├── fuzzing/
│   └── evidence/
```

Every proof should have:

- A unique requirement ID.
- The exact property being established.
- Its assumptions and preconditions.
- The source-code revision it applies to.
- The proof tool and version.
- The solver and version, where applicable.
- The proof result and reproducible invocation.
- Its dependencies on other proofs.
- Explicit unverified assumptions.

A passing proof from an old source revision must not count as evidence for a new binary. Humans have somehow managed to make that mistake repeatedly, so automate the association.
